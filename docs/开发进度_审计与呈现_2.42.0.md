### 顺手修掉的一个真 bug（重要）

`lib/core/checkoff.js` 的内容指纹函数一直是坏的：

```js
// 旧写法：把键名数组当 replacer 用
JSON.stringify(v, Object.keys(v || {}).sort())
```

replacer 数组只保留「出现在数组里的键」，**嵌套对象的键不在顶层数组里**，
于是 `{source:{file,locator}}` 被序列化成 `"source":{}`。后果：

- `lc_fact_amend` 改了事实的**出处定位**（P1 → P2），指纹不变；
- 签字单照样打「已核对」；
- 等于给「事后改证」盖章。

这正好落在对方那句判据上：**「没有会失败的检查的规矩 = 一句口号」** ——
旧代码有检查，但那个检查永远通过。已改成递归排序序列化，
并加反例测试 `test/checkoff_fingerprint.test.js`「核对后改出处定位 ⇒ 必须标为核对后被修改」。

> 真机后果：某案 153 条台账里 **97 条**属于「核对后被改」，以前显示为正常绿色。
> 现在顶栏会直接写：「卡点：97 条台账核对后又被改过，签字前必须重核」。

## 二、口径（写下来免得以后又各算一遍）

### 三段色

| 颜色 | 含义 | 判据 |
|---|---|---|
| 绿 `verified` | 人核过，且内容自那次核对后没变 | `done - stale` |
| 黄 `stale` | 核过，但之后内容被改过 | 指纹与核对时不一致 |
| 灰 `unverified` | 从来没有被任何人核过 | `total - done` |

三数相加恒等于 `total`（有测试钉住）。结论为「需修改 / 有疑问」也算绿 —— 那是人**明确判断过**，
和「没人看过」是两回事。

### 「上次动作」跳过的噪音

`client-mount` / `plugin-ready` / `tool-register` / `api-route` / `checkoff` / `case_new`
不算人的动作。理由：把这些算进去，顶栏永远显示「今天前端加载」或「今天建立案件」，看不出线索。

### 卡点只认一个来源

`lc_case_next` 说「下一步调哪个工具」（给模型），`lc_case_brief` 说「现在到哪了」（给人）。
两者**不各算一遍**：调 brief 时若传了 `next`，卡点以 next 为准。

## 七、2.43.0 追加：合同不止一份时的「不索引」

**用户反馈（2026-11-01）**：
> 合同审核中的索引条款处如果案件卷宗有多个文件，我可以只索引一个或几个；其它给出不索引的选项，
> 以便完成索引这一步；按现在的规则始终走不完这一步。

**根因**：`contractCandidates` 与 `next` 只认「已索引 / 未索引」两态。
卷宗里只要混进一份切不出「第X条」的附件（劳动合同、居间协议、保密承诺），
它就永远是「未索引」，索引这一步永远完不成。

**改法**（`clauses.json` 增加 `skipped` 数组，与 `files` 互斥）：

| 层 | 改动 |
|---|---|
| `core/clause.js` | `contractCandidates` 多了 `skipped/skipReason`；新增 `skipContract`（必须写理由，≥2 字）、`unindexClauses`；已索引的不能直接跳过 |
| `core/next.js` | 用 `undecided = 未索引 && 未跳过 && 文件存在` 判是否还挡路；索引已齐但还有未决定时降级为 priority 3 的提示，不再当作主卡点 |
| `tools/clause.js` | 新增 `lc_clause_skip`（含 `unskip`）、`lc_clause_unindex` |
| `server/api.js` | 新增 `clause.skip` / `clause.unindex`；`clause.candidates` 返回 `skipped` 计数 |
| `client.js` | 每行加「不索引 / 撤销不索引」；理由用**页内输入框**（⛔ 不用 `window.prompt`，Electron 里返回 null，本项目已踩两次） |

**测试** `test/clause_skip.test.js`（9 条），其中最关键的两条互为反例：
- 「★ 跳过后索引这一步必须能走完」——跳过后 `next.tool` 必须是 `lc_note_add`；
- 「反例：不跳过时那份附件必须仍然挡路」——不跳过时**不许**走到 `lc_note_add`，
  否则说明这个选项把问题藏起来了。

另有一条边界：**全部跳过**时仍然提示「没有切出条款」，不允许一字未审就交付。

**踩坑记录**：测试里曾把材料编号写死成 M1/M2，但扫描结果按文件名排序
（M1=保密协议、M2=劳动合同），导致断言指向了错误的文件。已改成 `midOf(A, '文件名')` 按名取号。

## 八、2.44.0：修改意见以 Word 批注输出

**需求（2026-11-01）**：给实际修改意见增加批注功能，把修改意见以批注形式输出。
**口径（用户选定）**：保留现有红线 + 额外加批注；批注正文 = 条款号 + 风险级别 + 问题 + 建议。

### 做了什么

新增 `lib/core/comments.js`，并在 `redline.js` 的生成管线上接入。OOXML 批注要四件套齐备，
缺一个 Word 就报「内容无法读取」：

| # | 组成 | 落点 |
|---|---|---|
| ① | `word/comments.xml` | `buildCommentsXml()` |
| ② | `[Content_Types].xml` 注册 Override | `registerComments()` |
| ③ | `word/_rels/document.xml.rels` 关系 | `registerComments()`（id 取现有最大值 +1，不撞车） |
| ④ | 正文 `commentRangeStart` / `commentRangeEnd` / `commentReference` | `anchorComment()` |

### 踩到的三个坑（都已用测试钉住）

1. **锚点坐标会错位**。`anchors` 记的是原文偏移，但 `jobs` 已经改过 XML，
   整条替换会把多段压成一段、长度变短 ⇒ 按原坐标切会落进**别的段落**。
   实测现象：两条批注只插上第一条。
   最终解法：**不按坐标认段，按段落纯文本认段**——改完之后重扫段落列表，
   用「这段文本里有没有这句原文/新文」配对。
2. **不能拿 XML 做子串匹配**。一句话常被拆成多个 `<w:r>`（改动处两侧格式不同），
   XML 里是 `…100 万元，</w:t>…<w:t>签订后 3 日内…`，直接 `indexOf` 整句永远找不到。
   必须先 `paraText()` 去掉标签再比（只取前 8 个字，避开标点差异）。
3. **空批注框**。最初 `fix` 回退到 `newText`，于是任何一次纯改字都会生成一个
   既没问题、也没建议的批注框。判据改成：只有 `issue` 或**显式给的** `fix` 才算「有话说」。
   这条是被测试的反例逼出来的（`反例：没写 issue 也没有 fix 时不生成空批注`）。

### 验证

- `test/comments.test.js` 11 条：四件套齐备、条数与条款数一致、批注挂对条款、
  三个 XML 全良构、`registerComments` 幂等、id 不冲突、标签顺序、
  `comments:false` 退回纯红线、特殊字符转义。
- OOXML 规范硬校验（id 三处一致 / RangeStart→RangeEnd→Reference 顺序 / 关系 id 无重复）全过。
- 真实案件链路端到端：建案 → 扫材料 → 索引 → 登记 2 条意见 → 生成修订版，
  产出 `修订版_服务合同.docx`，批注 2 条、锚点 2 处。

> ⚠️ 本机沙箱起不了 Word GUI，所以「Word 能否打开」这一条**没有做人工点击验证**，
> 依据是 OOXML 规范校验 + 三个 XML 良构性检查。首次真实使用时建议先打开看一眼。

## 九、2.45.0：按条款区分「批注」与「修订」

用户看完 2.44 的 Word 截图后指出两条关键问题：
1. 图里原文没真被删——**「删除线 + 下划线」两种格式串在一起**，读者要自己判断哪半句是废稿；
2. 更根本的：**「如果是以批注形式的一般不会有删除的内容；即我不会对正文进行修改」**。

结论：**批注模式下正文一个字都不该动**。而「有些条款是批注，有些条款是修订」，所以需要**逐条**决定。

### 做了什么

| 层 | 改动 |
|---|---|
| 数据 | 意见（notes）新增 `apply` 字段：`comment`（默认）/ `redline`；`normalizeApply()` 归一 |
| 引擎 | `doRevise` 里 `redlineEdits = edits.filter(e => e.apply === 'redline')`，其余只走批注 |
| 措辞 | 只批注时写「**建议改为**」；改正文时写「建议」（正文已改好，不能让人误会） |
| 判据 | 「既没修订、也没批注」才报错；**全批注零修订是合法产物** |
| 接口 | `lc_note_add` 加 `apply` 参数；`utils note.setApply` 一键切换；`lc_contract_revise` 支持 `draftsApply` |
| 界面 | 意见行两个按钮「批注 / 改正文」，当前态用实心区分 |

### 两处判据写反的教训

第一版用 `e.apply !== 'comment'` 过滤改正文的编辑——**没传 apply 的调用方会被默认当成改正文**，
等于把「替客户改稿」变成默认行为。改成白名单 `e.apply === 'redline'` 才对。
这类「反向默认」在布尔判断里特别容易写错，已用测试钉住（`★ 默认 apply=comment：正文一个字不动`）。

### 连带发现

- `doRevise` 的返回体缺 `ok` 字段，`reviseContract` 之外直接调用时拿不到成功标志（已补）；
- 片段级修订（patch）语义天然是改正文，已显式传 `apply:'redline'`，不吃新默认；
- AI 草稿默认也走批注（草稿尚未采纳，改正文越权），要出改好稿用 `draftsApply:'redline'`。

## 十、2.46.0：按钮为什么「仍然没有」

用户两次反馈看不到「批注 / 改正文」按钮，两次根因完全不同：

| 版本 | 症状 | 真因 |
|---|---|---|
| 2.45.0 第一版 | 完全看不到 | 只改了**登记表单视图**（`form`）的列表，而默认是**全文视图**（`FullTextReview`）——律师日常就在全文里 |
| 2.45.0 第二版 | 还是看不到 | 按钮挂在了「已登记意见」上（`myNotes.length > 0`），而用户截图里是 **`AI 草稿 2`**，还没保存成正式意见 |

第二版的设计本身就是错的：正确顺序是**先决定形式，再保存**，而不是保存完再去切换。

### 改法

- 按钮**始终可见**；
- 未登记意见时，选择先存在页面状态 `applyChoice[file#clause]`；
- 点「保存」时随 `note.adopt` 一起写进台账（`apply` 字段一路透传到 `addNote`）；
- 已登记意见则直接调 `note.setApply` 立即生效。

### 测试

两条互为补充，都用**默认参数**渲染（不是只测某个分支）：
- `★ 默认视图（全文）必须出现「批注」「改正文」两个按钮`
- `★ 只有 AI 草稿、还没登记意见时，按钮也必须出现（用户截图就是这个状态）`

### 教训

同一个功能在一屏里出现两次（两个视图各一份渲染代码），**只改一处就等于没做**。
凡「同一份 UI 有两个实现」的地方，测试必须覆盖**用户实际会看到的那个**，
并且要用默认参数渲染——否则测试能全绿，用户还是看不到。

## 十一、2.47.0：按钮不出现的真正根因（条款号键对不上）

用户第三次反馈看不到按钮时，截图里同时暴露了另一个错误：

> 保存失败：合作投资协议（三方-草案）.docx 第一条 已登记过相同问题 N1。
> 如果你是想修改这一条，请用「更新」…

但界面上根本没有「更新」按钮——**这条报错在让人点一个不存在的东西**。
两个现象同一个根因：

### 根因：`clauses.json` 里同一条款有两个编号

真实案件里条款索引是这样的：

```
1, 2, 3, 第一条, 第二条, …, 第十五条
↑ 前言里的编号列举     ↑ 正文条款
```

- 意见登记时记的是 `第一条`；
- 而渲染循环里某处 `c.no` 是 `1`；
- 界面按 `文件名#条款号` 建索引 ⇒ `合同.docx#第一条 ≠ 合同.docx#1` ⇒ `myNotes` 为空；
- 于是：按钮不显示（依赖 `myNotes`）、`updateId` 丢失（依赖 `myNotes[0].id`）⇒ 误报重复。

### 修了三层

| 层 | 改法 |
|---|---|
| 索引（根因） | `splitClauses`：**存在「第X条」体系时，纯数字编号一律不视为条款**（那是前言的列举）；只有在完全没有「第X条」的自动编号合同里才用数字 |
| 索引（加固） | 同一文档里条号重复（正文+附件各一套）只保留第一次出现的 |
| 界面 | 键归一：`noKey()` 把「1」「第一条」都折算成 `N1` 再拼键；兜底键也统一用 `noKey`（原来兜底用旧写法 `'#'+norm(c.no)`，改了主键却漏了兜底，草稿永远匹配不到） |

### 教训（三条，都值得记住）

1. **「键对不上」的症状会伪装成完全无关的 bug**：按钮不显示、`updateId` 丢失、误报重复，
   看起来是三个功能坏了，其实是一个键的问题。先查数据形态，别急着改 UI。
2. **改主键必须同时改兜底键**。`draftsBy.get(k) || draftsBy.get('#'+norm(c.no))` 里
   前半句我改了、后半句没改，草稿匹配直接失效——这条被现有测试当场抓住。
